# Internationalization

Gitrune uses `i18next` with `react-i18next`. The selected language is stored with the other non-secret application settings in local SQLite and changes immediately without restarting the desktop app.

## Supported locales

- `en` — English; complete fallback language
- `pl` — Polish
- `uk` — Ukrainian

Locale resources live in `src/i18n/resources/`. Keep their object shape aligned with the English resource. Missing translated keys intentionally fall back to English.

## Adding or changing UI text

1. Add a semantic, feature-scoped key to `en.ts`.
2. Add the same key to the other locale resources when a reviewed translation is available.
3. Render it with `useTranslation()` and `t("feature.key")`.
4. Use i18next interpolation and plural forms (`_one`, `_few`, `_many`, `_other`) rather than joining translated fragments.
5. Do not translate paths, SHAs, branch/ref names, command previews, or raw Git output.
6. Run `npm run verify`.

New locales must be added to `supportedLanguages` in `src/i18n/index.ts`, the Settings language selector, and Rust settings validation. A locale must have a stable language code before it is persisted.

## Translation status

The application shell, runtime notice, settings, commit options, repository collection, status bar, and the primary Changes/Graph/Stashes/Worktrees surfaces have Polish and Ukrainian translations. Existing specialist workflow copy falls back to English while it is migrated to semantic keys. The remaining migration is tracked in `REQUIRED_WORK.md`; fallback prevents partial resources from rendering raw keys.
